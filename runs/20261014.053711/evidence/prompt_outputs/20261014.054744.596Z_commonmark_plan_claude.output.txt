# FEATURE: List Items

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Parse list items with bullet and ordered markers, content-offset indentation rules, empty items, start numbers and lazy continuation. |
| Depends On  | FEATURE-Setext-Headings.md |
| Provides    | list item container |
| Consumes    | block-type registry |

## Questions

- None.

## Purpose

Implement the List items section of the spec as a registered container block. Grouping items into lists and tight or loose rendering belong to the lists story.

## Rules

- A bullet marker is `-`, `+` or `*`. An ordered marker is 1 to 9 digits followed by `.` or `)`. The marker may have up to three spaces of indentation. At least one space or tab must follow the marker unless the item is empty.
- Content offset W+N: W is the marker width and N is the number of spaces after it, if that is 1 to 4. If 5 or more spaces follow the marker and the rest of the line is not blank, the item starts with an indented code block and N is 1. If the rest of the line is blank, the item starts with a blank line and N is 1.
- Column-aware indentation with tab stop 4 is used throughout. Continuation lines must be indented at least W+N columns relative to the containing block. Blank lines continue the item.
- An item can begin with at most one blank line: a second consecutive blank line right after an empty marker ends the item.
- Interruption: when a list item would interrupt a paragraph, it must not start with a blank line, and an ordered item must start with number 1. A thematic break line is never a list item.
- Laziness: an unindented line that is paragraph continuation text stays in the item's open paragraph.
- Ordered items carry a start number (leading zeros allowed). Output is `<li>` elements; a loose item wraps paragraphs in `<p>`.

## Reads

- Lines handed to the block engine.

## Writes

- List item nodes in the block tree.

## Programmatic Acceptance

The corpus section examples need list grouping and tightness, so it is gated in the lists story. The checks here are bounded and avoid tight-list paragraph rendering.

# FEATURE: Lists

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Group list items into lists, compute tight and loose rendering, and gate the block-structure corpus sections. |
| Depends On  | FEATURE-List-Items.md |
| Provides    | list container, tight/loose computation |
| Consumes    | list item container |

## Questions

- None.

## Purpose

Implement the Lists section of the spec, and gate the block-structure sections whose examples need lists.

## Rules

- Consecutive items of the same type form one list. Two items are of the same type if both are bullets with the same character, or both are ordered with the same delimiter. Changing the bullet character or the ordered delimiter starts a new list.
- The start number of an ordered list is that of its first item. The `start` attribute is emitted only when it is not 1.
- Items may be separated by any number of blank lines. Items need not be indented identically, as long as none is indented enough to be inside the previous item.
- A list can interrupt a paragraph; an ordered list does so only if it starts at 1.
- A list is loose if any two of its items are separated by a blank line, or if any item directly contains two block children with a blank line between them. Otherwise it is tight. Blank lines inside fenced code, inside a nested list's own children, or inside a block quote do not make the outer list loose. Link reference definitions do not count as blocks for this purpose.
- In a tight list the paragraphs of the items render without `<p>` tags. In a loose list they render with them. Nested lists decide their own tightness.

## Reads

- List item nodes from the block tree.

## Writes

- List nodes and the tight flag in the block tree.

## Programmatic Acceptance

# FEATURE: Tabs

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Make tabs behave as four-column tab stops for block structure while leaving tabs untouched in content, and gate the remaining corpus sections. |
| Depends On  | FEATURE-Lists.md |
| Provides    | tab-stop-aware column handling |
| Consumes    | block container rules |

## Questions

- None.

## Purpose

Implement the Tabs section of the spec, audit every block rule's column handling, and gate the corpus sections whose examples needed all block and inline stories.

## Rules

- Tabs are never expanded into spaces in output. Inside code and text, a tab is passed through as a literal tab.
- Where spaces define block structure (indented code, block quote markers, list marker spacing, list item continuation, ATX heading and thematic break separators), a tab advances to the next multiple of 4 columns.
- A tab that is only partly consumed (for example after a `>` marker or a list marker) leaves its remaining columns as virtual spaces of indentation for the rest of the line.
- All block start and continue rules use the one shared column-aware helper from the block engine.

## Reads

- Lines handed to the block engine.

## Writes

- No new nodes; this story corrects column handling in existing rules.

## Programmatic Acceptance
