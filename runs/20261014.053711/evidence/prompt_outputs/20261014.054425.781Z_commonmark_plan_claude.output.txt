# FEATURE: Code Spans

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Parse code spans and establish the left-to-right inline scanner with code, autolink and raw HTML precedence. |
| Depends On  | FEATURE-Autolinks.md, FEATURE-Raw-HTML.md |
| Provides    | code span inline construct, inline scanner loop |
| Consumes    | autolink inline construct, raw inline HTML construct |

## Questions

- None.

## Purpose

Implement the Code spans and Inlines sections of the spec, and the inline scanner loop that later inline stories extend.

## Rules

- The scanner walks the text left to right. At a backtick, `<` or other special character it tries the matching construct; the first construct that matches wins.
- A backtick string is a maximal run of backticks. A code span opens at a backtick string and closes at the next backtick string of exactly the same length. If none exists, the opening run is literal text.
- Content normalization: convert line endings to spaces; then, if the content both begins and ends with a space and is not entirely spaces, remove one space from each end. Only U+0020 counts, not other whitespace. Interior spaces are not collapsed.
- Content is HTML-escaped. Backslash escapes and entities are inert inside code spans.
- Code spans, raw HTML and autolinks have equal precedence: whichever starts first is parsed first. Bracket and emphasis handling is lower precedence and is added by later stories.

## Reads

- Inline text of paragraphs and headings.

## Writes

- Code nodes in the inline tree.

# FEATURE: Backslash Escapes

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Implement backslash escapes of ASCII punctuation in text and expose a shared unescape helper for destinations, titles and info strings. |
| Depends On  | FEATURE-Code-Spans.md |
| Provides    | backslash escape inline rule, shared unescape helper |
| Consumes    | inline scanner loop |

## Questions

- None.

## Purpose

Implement the Backslash escapes section of the spec.

## Rules

- A backslash followed by any ASCII punctuation character yields that character as plain text with no Markdown meaning, so it cannot start emphasis, a link, a code span, a heading, a list or a tag.
- A backslash followed by any other character is a literal backslash.
- A backslash at the end of a line is a hard break marker, handled by the line-breaks story.
- A backslash that is itself escaped leaves the next character unescaped.
- Backslash escapes are inert in code spans, code blocks, autolinks and raw HTML.
- The shared `unescape` helper applies the same rule to link destinations, link titles and fenced code info strings, and is reused by those stories.

## Reads

- Inline text of paragraphs and headings.

## Writes

- Plain text nodes in the inline tree.

# FEATURE: Entities

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Decode HTML5 named entities and decimal and hexadecimal numeric character references, with a shared helper for destinations, titles and info strings. |
| Depends On  | FEATURE-Backslash-Escapes.md |
| Provides    | entity decoding rule, shared entity helper |
| Consumes    | inline scanner loop |

## Questions

- None.

## Purpose

Implement the Entity and numeric character references section of the spec.

## Rules

- A named reference is `&`, a name present in `html.entities.html5` with a trailing semicolon, and `;`. References without a semicolon (for example `&copy`) and unknown names are not recognized and stay literal, with `&` escaped as `&amp;`.
- A decimal reference is `&#` plus 1 to 7 digits plus `;`. A hexadecimal reference is `&#` plus `x` or `X` plus 1 to 6 hex digits plus `;`.
- Invalid code points (surrogates, above U+10FFFF) and U+0000 are replaced with U+FFFD.
- A decoded character is always plain text and never structure: `&#42;` cannot start emphasis, a list or a thematic break. The decoded text is HTML-escaped on output.
- References are inert in code spans and code blocks, and are decoded in link destinations, titles and fenced info strings. The shared helper provides that for those stories.
- Some named entities decode to two code points; both are emitted.

## Reads

- Inline text of paragraphs and headings.

## Writes

- Plain text nodes in the inline tree.

## Programmatic Acceptance

The corpus section needs links, definitions, fenced code, indented code and emphasis, so it is gated in the tabs story. The checks here are bounded and derive their expectations from bound inputs.

# FEATURE: Emphasis

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Implement the delimiter stack, flanking rules and the Appendix process-emphasis algorithm for emphasis and strong emphasis. |
| Depends On  | FEATURE-Entities.md |
| Provides    | delimiter stack, process_emphasis procedure |
| Consumes    | inline scanner loop |

## Questions

- None.

## Purpose

Implement the Emphasis and strong emphasis section of the spec using the Appendix algorithm directly.

## Delimiter stack

- On a run of `*` or `_`, insert a text node holding the run and push a stack entry with: delimiter type, run length, original length, active flag, and `can_open` and `can_close`.
- The stack also accepts `[` and `![` entries so the links story reuses it.
- Flanking: a run is left-flanking when it is not followed by Unicode whitespace and either is not followed by punctuation, or is followed by punctuation and preceded by whitespace or punctuation. Right-flanking is the mirror. Line start and end count as whitespace. Punctuation means Unicode categories `P*` and `S*` via `unicodedata`.
- For `*`: `can_open` is left-flanking and `can_close` is right-flanking. For `_`: `can_open` is left-flanking and (not right-flanking or preceded by punctuation); `can_close` is right-flanking and (not left-flanking or followed by punctuation).

## process_emphasis(stack_bottom)

- Maintain `openers_bottom` per delimiter type, indexed by closer length mod 3 and whether the closer can also open.
- Find the first potential closer, then search back for a valid opener: same type, can open, and the multiple-of-3 rule satisfied (if either can both open and close, the sum of original lengths must not be a multiple of 3 unless both are).
- If found, use strong when both runs have length of at least 2, otherwise regular. Wrap the nodes between opener and closer, remove delimiters between them, and consume 1 or 2 characters from each side, removing empty entries.
- If not found, lower `openers_bottom`, drop the closer if it cannot open, and advance.
- At the end remove everything above `stack_bottom`. Leftover delimiters stay as literal text.

## Reads

- Inline text of paragraphs and headings.

## Writes

- Emphasis and strong nodes in the inline tree.

## Programmatic Acceptance

# FEATURE: Link Reference Definitions

| Field       | Value |
|-------------|-------|
| Version     | 20261014 V1 |
| Description | Extract link reference definitions when a paragraph closes and provide the document-wide reference map and label normalization. |
| Depends On  | FEATURE-Block-Engine.md |
| Provides    | reference map, normalize_label |
| Consumes    | block tree builder |

## Questions

- None.

## Purpose

Implement the Link reference definitions section of the spec and the label matching shared with links and images.

## Rules

- When a paragraph closes, repeatedly parse a definition at the start of its text: up to three spaces of indentation, a link label, a colon, optional whitespace with up to one line ending, a link destination, optional whitespace with up to one line ending, and an optional title. Nothing else may follow on the final line.
- A link label has 1 to 999 characters, at least one non-whitespace character, and no unescaped brackets. A destination is either `<...>` with no line ending or unescaped `<` or `>`, or a nonempty run with no spaces or control characters and balanced parentheses. An empty `<>` destination is allowed.
- A title is double-quoted, single-quoted or parenthesized, may span lines, must not contain a blank line, and must be separated from the destination by whitespace.
- If the title does not parse, but the destination ends its line, the definition has no title and the rest of the paragraph remains. If anything else follows the title on its line, the whole attempt fails and the text stays a paragraph.
- The first definition for a normalized label wins. Definitions in containers go into the same document-wide map. A definition cannot interrupt a paragraph, which follows from extracting only at the start of the paragraph's text.
- Remaining text becomes a paragraph. A paragraph that consists only of definitions disappears.
- `normalize_label` strips the brackets, applies `str.casefold()`, strips, and collapses internal spaces, tabs and line endings to one space. Matching compares normalized strings, not parsed inlines.
- Destination and title go through the shared unescape and entity helpers. The stored destination is percent-encoded at render time by the link story.

## Reads

- Closed paragraph text.

## Writes

- Entries in the reference map.
